## 1. Giving a coding agent access to GitHub (3:05)

There are several valid ways to let an agent work with GitHub:

- **GitHub MCP server**: gives Claude a set of GitHub tools (you have to manage the connection and authorization).
- **IDE integrations**: VS Code or Cursor extensions.
- **GitHub skill**.
- **GitHub CLI (`gh`)**: the approach used from now on in this course.

**Why `gh`:**

- Claude already controls the machine through its Bash tool, so once `gh` is installed it can create repos, open PRs, merge, and manage everything from the terminal with no extra connection setup.
- Models are already well trained on `gh`, so no special skill or instructions are needed. You only describe your workflow. (Analogy: you don't teach a model how to format an email, you just give it your style and requirements. Anything you repeat often goes into a skill or `CLAUDE.md`.)

**Setup:** ask Claude Code (or OpenCode) to check whether `gh` is installed, install it if missing, and log you in. Both **installed** and **logged in** are required.

**Homework:** commits made by Claude list Claude as a co-author. Find out which setting in `settings.json` turns that off.

## 2. Hands-on: creating a demo repo (9:18)

1. In a new folder, ask Claude: create a new project for exam prep that holds only Markdown files, write a README, and put it on GitHub (private).
2. Claude creates the folder, README, and `.git`, then pushes the repo.
3. Follow-up prompts, all carried out through `gh`: "Is it live?", "Rename the repo to `class-demo` and make it public."

At this point all work is on the **main** branch. That's like editing a shared Google Doc directly.

## 3. New requirement: only Markdown files, and no direct commits to main (12:42)

Requirements:

- Every file in the project must be Markdown (`.md`).
- Nothing gets committed directly to `main`. Claude creates a branch, does the work there, opens a PR, and changes reach `main` only when the PR is merged.

Asking Claude to "share all options" gave these approaches:

| Option | What it does | Limitation |
|---|---|---|
| `CLAUDE.md` / contributing rule | Tells Claude the workflow | Only shapes Claude's behaviour; can be ignored |
| `.gitignore` | Keeps unwanted files out of git | Local only |
| Claude hooks (e.g., PreToolUse) | Blocks Claude from creating non-`.md` files | Only works for Claude on your machine |
| Permission rules | Restricts Claude's actions | Same, local to Claude |
| **GitHub Actions** | Runs checks on GitHub whenever an event occurs | Enforced for everyone |

### What GitHub Actions is (16:25)

- You define a **workflow** that runs whenever a chosen **event** happens (a push to main, a PR being opened, etc.).
- When the event fires, GitHub starts a **virtual machine**, runs the commands in your workflow, reports the result, and shuts the machine down.
- Because the workflow is just commands, it can do anything: check files, run tests, and so on.
- Think of it as **a robot living in your repo** that does a defined job every time something happens.

## 4. Git basics for beginners (19:39)

- **main**: the primary copy of the project.
- **Branch**: a copy of main where you make your changes.
- **Pull request (PR)**: a request to review your branch and bring its changes into main.
- **Merge**: bringing the approved PR's changes into main.

Workflow: branch → make changes → open PR → robot checks files (✔ or ✘) → fix until it passes → merge.

## 5. Plan mode: when to use it (22:12)

- Use it when a change is large or you need to investigate first.
- Skip it for small, clear changes.
- If the requirements are unclear, keep discussing first. A useful prompt is: "I'm a bit confused. First explain in your own words what I'm trying to do, and what the actions are." Adding "I'm completely new to this" keeps the explanation non-technical.
- In this case the explanation made everything clear, so plan mode wasn't needed. The prompt was: "Implement it and explain every step to me."

## 6. What Claude built (28:33)

- **`.gitignore`**: a rulebook of local files that shouldn't be uploaded.
- **`.github/workflows/<name>.yml`**: the robot's configuration, written in YAML (a machine-readable format like Markdown).
  - `name`: any name, e.g., "markdown only".
  - **Trigger (`on`)**: runs whenever a PR targets `main`.
  - **Jobs/steps**: plain bash commands (you could run them in your own terminal) that list the changed files and fail if any isn't `.md` (e.g., `.txt`, `.py`, `.csv`).
- **Branch protection** on `main`, so changes have to go through a PR whose checks pass.
- Claude also tested the setup itself.

## 7. Testing the robot (31:40)

1. "Create a new branch named `prep-plan` and push it to GitHub." The branch now shows on GitHub next to `main`.
2. "In this branch add a new `.docx` file and push it. Don't open a PR."
   - **Tip:** to edit a previous message in Claude Code, press **Esc twice**, use the arrow keys to pick the message, press Enter, and choose to restore the conversation.
3. The file exists only on the branch, not on `main`.
4. "Now make a PR to main." The PR appears under the repo's **Pull requests** tab.
5. Result: the check **failed**, the merge was **blocked**, and the logs show the same commands from the workflow plus an error naming the non-Markdown file.
   - Not a merge conflict. The rule simply doesn't allow it (like a monitor at the classroom door: no ID card, no entry).
6. Fix: rename or convert the file to `README2.md` (deleting it would also work). Claude commits and pushes, the check re-runs, it turns **green**, and the PR can be merged.

## 8. The concept: Continuous Integration (CI) (41:27)

- **CI** means that every change automatically triggers a machine that runs your defined checks and reports pass or fail before anything reaches `main`.
- Analogy: quality control on a packet of chips (is the packing right? is it expired?). Every check has to pass. If one fails, you get a ✘.
- CI can be set up in many places. GitHub Actions is the most common.
- What we've learned so far: **GitHub Actions**, a **virtual machine** per run, and a **workflow/script** that runs inside it.

## 9. Can Claude run inside that VM? (45:08)

- **Can Claude run in a VM?** Yes. It only needs a computer.
- **Could I answer Claude's questions there?** Every run gets its own short-lived VM that's torn down afterwards, so there's no practical way to answer interactively.
- **Why would I want to?** The point of CI is that nobody is watching. Human-in-the-loop is a separate concept.
- So the real need is a mode where **Claude doesn't interact with you at all**: it takes the task, finishes it, and exits.
- A Claude that wakes up on an event, does the work, and goes back to sleep on another machine is a **CI worker**.

## 10. Quiz recap (51:38)

1. *Why didn't the robot fail when the `.docx` was pushed to `prep-plan`?* Its trigger is a PR to main, not a branch push.
2. *What blocked the merge?* **Branch protection**. The workflow only reports ✔/✘ and has no authority beyond that.
3. *Enforcement applies to admins too. What does that mean for you as the owner?* You have to follow the rule as well.
4. *Weak spot of this setup?* A PR can edit the workflow file itself, so anyone could change or weaken the rule.

## 11. Headless (non-interactive) mode (56:42)

- `claude` starts **interactive mode**.
- `claude -p "<prompt>"` runs in **non-interactive / headless mode**: Claude takes the prompt, does the work, prints the result, and returns control of the terminal without waiting for a follow-up.
- Why it matters: on a PR or in a workflow you can have Claude fix errors, review changes, or replace hard-coded steps, with Claude running headless on GitHub's runners.

## 12. Demo: installing Claude's GitHub App (1:03:07)

1. In the repo, run Claude Code's slash command **`/install-github-app`** ("Set up GitHub Actions for a repository"). It handles auth, login on the VM, and the workflow files.
2. It checks for `gh`, confirms the repo, and opens the browser to install the **Claude GitHub App**. You can grant access to all repos or only selected ones.
3. Choices along the way: let Claude create the workflow, use `@claude` to talk to it, and authenticate with an **API key or a subscription** (a subscription was used here; OpenCode would use your model provider's API key).
4. Claude creates a branch, adds the workflow files, sets a token, and opens a **PR**. Merge it to finish setup.

**Two workflow files are added:**

- **Claude Code Review**: triggers on pull requests and reviews them. Its config ends with a customizable prompt.
- **Claude**: triggers when `@claude` is mentioned in an issue or PR comment, and runs Claude with that comment as the task.

## 13. Why did the Markdown check pass for `.yml` files? (1:10:06)

- The setup PR added `.yml` files, yet the markdown-only robot passed.
- Reason: the workflow had a rule to **skip the `.github/` folder**. (Like the door monitor checking every student's card but not the teacher's.)
- **Architect's question: is that rule correct?** The project's goal is notes in Markdown. Notes never go in `.github/`, which is a configuration folder, so excluding it is the better choice (option 2). You're responsible for every rule Claude adds, so review them against your goal.

## 14. Demo: Claude solving a GitHub issue (1:18:09)

- An **issue** is how you report a problem or start a discussion on GitHub. The owner or maintainer resolves and closes it.
- Created an issue ("Write CI notes"), then commented: **`@claude work on this issue and create a PR, then comment.`**
- Claude replied that it had started, ran in the VM (about 45 seconds; the logs are viewable), wrote the notes, pushed a branch, and offered a "Create PR" button.
- When the PR was opened, the **Claude Code Review** workflow ran on it automatically. After merging, the new Markdown notes file was on `main`.

**Takeaway:** the repo, the machine, and Claude are all somewhere else. You just assign a task and look at the output.

**Triggers can be anything:** a schedule (e.g., "wake up at midnight and do X"), a PR, a push, an issue, or custom events.

## 15. Customizing the CI worker (1:24:43)

There are two parts:

1. **Context**: what Claude sees while it works: `CLAUDE.md`, rules, skills, MCP servers, hooks, memory, and the settings file.
2. **Config**: inputs, outputs, model, and so on (next class).

**Experiment: does headless mode load context? (1:28:05)**

- Ran `claude -p "What is my favorite pet?"`. Claude didn't know.
- Added "I like eagles" to `CLAUDE.md` and asked again. Claude now knew about eagles, which shows **`CLAUDE.md` is loaded in headless mode**.
- So when Claude runs headless in CI on a repo, it picks up the repo's `CLAUDE.md`, skills, MCP config, hooks, and rules.
- Good context matters **even more** in CI because there's no human watching, only the final output.

- OpenCode users: figure out how to do the same with OpenCode.
